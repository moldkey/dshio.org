>

## 1 範圍

本標準規定了 DSHIO 認證的申請條件、審核流程、證書內容、有效期與撤銷規則。

本標準適用於申請 DSHIO 認證的插件作者與執行認證的 DSHIO 自身。

**本標準不規定技術要求** —— 技術要求見 DSHIO/T 10；測試方法見 DSHIO/T 20 與 DSHIO/T 21。

### 1.1 實施獨立性聲明

本標準規定的認證**只判定是否符合標準**，不判定插件的好壞、不推薦使用、不背書作者。

獲得認證的插件仍可能不適合特定用途。認證不構成任何形式的保證。

## 3 術語和定義

DSHIO/T 00—2026 界定的術語適用於本文件。

**本文件補充定義：**

### 3.1 申請人
applicant

提出認證申請的主體。必須是插件的合法發佈者。

### 3.2 認證範圍
certification scope

認證覆蓋的具體內容：插件名、版本、DSH 版本、測試階段範圍、模型（若含 T5）。

**認證範圍之外的一切不在認證效力內。**

### 3.3 證書
certificate

證明認證範圍內符合性的文件。含唯一編號與可查詢地址。

### 3.4 有效期
validity period

證書生效至失效的時間段。

### 3.5 撤銷
revocation

在有效期內使證書失效的行為。

### 3.6 暫停
suspension

在有效期內臨時中止證書效力的行為。

## 4 認證級別

### 4.1 三級設計

| 級別 | 名稱 | 覆蓋 | 判定要求 |
|---|---|---|---|
| **L1** | 靜態符合 | T0 | 無 critical 不符合 |
| **L2** | 可安裝 | T0–T4 | 無 critical 不符合，且 T1–T4 全部通過 |
| **L3** | 完整符合 | T0–T5 | L2 + 人工條款 + T5 全過 |

### 4.2 級別與範圍的關係

**L1、L2 與模型無關。** 其證書不註明模型。

**L3 必須註明模型。** 一個插件在 A 模型上通過 L3，不代表在 B 模型上也通過。

### 4.3 當前規劃

**當前只計劃開放 L1 與 L2。** L3 涉及模型成本與隨機性，**待規劃**。

L3 已寫入標準，但尚未排入實施計劃。

## 5 申請條件

### 5.1 必備條件

申請人必須同時滿足：

| # | 條件 | 核驗方式 |
|---|---|---|
| 1 | 已註冊 DSHIO 賬號 | 郵箱或 GitHub 驗證 |
| 2 | 是插件的合法發佈者 | 見 5.2 |
| 3 | 插件已公開發佈且可安裝 | registry 可查 |
| 4 | 已自行完成一次靜態檢查且無 critical 不符合 | 提交檢查報告連結 |
| 5 | 已閱讀並接受認證條款 | 勾選確認 |

### 5.2 發佈者驗證

三種方式，任選其一：

| 方式 | 操作 | 適用 |
|---|---|---|
| **npm 維護者驗證** | 用 registry 中記錄的 maintainer 郵箱接收驗證碼 | npm 包 |
| **倉庫權限驗證** | 在倉庫 README 或指定 issue 中放入一次性驗證碼 | GitHub 包 |
| **雙向確認** | 從插件 README 中聲明的聯繫郵箱發出申請 | 兜底 |

**驗證碼有效期 24 小時，一次性。**

**未通過發佈者驗證的申請一律駁回。** 理由：防止給他人插件頒發證書。

### 5.3 不接受的情形

| 情形 | 處理 |
|---|---|
| 插件源碼不公開且作者拒絕提供可審查的說明 | 只能申請 L1/L2（不涉及源碼審查）|
| 插件已被撤銷認證且未滿 90 天 | 不受理 |
| 同一版本重複申請 | 不受理，已認證狀態可直接查詢 |
| 申請人與插件無關聯 | 駁回 |

## 6 審核流程

### 6.1 流程圖

```
1. 提交申请
      ↓
2. 形式审查（3 个工作日内）
      ↓ 不通过 → 告知原因，可修改后重提
3. 技术检验（L1：即时；L2：1-3 个工作日）
      ↓ 不通过 → 出具不符合清单
4. 出具报告
      ↓
5. 申请人确认（7 天内）
      ↓ 逾期视为放弃
6. 证书签发
      ↓
7. 公开登记
```

### 6.2 形式審查

檢查：
- 申請材料齊全
- 發佈者驗證通過
- 插件在 registry 可查
- 申請的級別與範圍明確

**不涉及技術判定。**

### 6.3 技術檢驗

**按申請級別執行對應階段：**

| 級別 | 執行的階段 | 重複次數 |
|---|---|---|
| L1 | T0 | 1 次 |
| L2 | T0–T4 | **2 次，判定必須一致** |
| L3 | T0–T5 | T0–T4 兩次，T5 三次全過 |

**全部測試必須符合 DSHIO/T 21 的條件，並記錄環境指紋。**

### 6.4 出具報告

報告必須包含：

1. 認證範圍（插件名、版本、DSH 版本、級別）
2. 環境指紋
3. 逐條結果（條款號、狀態、證據）
4. 總體判定
5. 例外清單（若有）
6. 測試日期與執行者標識

**不得只給結論不給證據。**

### 6.5 申請人確認

申請人收到報告後 7 天內確認。確認即表示：
- 接受報告內容
- 同意在認證範圍內使用標誌
- 同意公開登記

**逾期未確認視為放棄本次申請。**

### 6.6 簽發

通過後簽發證書，寫入公開登記冊。

## 7 證書

### 7.1 內容

| 項 | 內容 |
|---|---|
| 證書編號 | `DSHIO-<級別>-<年月>-<序號>`，例如 `DSHIO-L2-202612-0007` |
| 插件名 | npm 包名或 `github:owner/repo` |
| 插件版本 | 精確版本號 |
| 認證級別 | L1 / L2 / L3 |
| 認證範圍 | 覆蓋的階段 |
| DSH 基準版本 | 例如 `0.2.2-rc.1` |
| 環境指紋 | 完整字符串 |
| 模型（L3 必填）| 模型 ID + 版本 |
| 發證日期 | YYYY-MM-DD |
| 有效期至 | YYYY-MM-DD |
| 查詢地址 | `https://dshio.org/verify/<證書編號>` |
| 報告連結 | 完整報告的公開地址 |

### 7.2 有效期

| 級別 | 有效期 | 理由 |
|---|---|---|
| L1 | 12 個月 | 靜態結構變化慢 |
| L2 | 6 個月 | DSH 版本變化快，行為可能失效 |
| L3 | 3 個月 | 模型與插件都在快速變化 |

**有效期從簽發日起算。**

### 7.3 續期

有效期屆滿前 30 天可申請續期。

**續期需重新執行對應級別的檢驗。** 插件版本變更時，不得以舊報告續期。

### 7.4 證書不得轉讓

證書綁定具體插件與版本。插件轉手時，證書不隨之轉移，需重新申請。

## 8 撤銷與暫停

### 8.1 撤銷的情形

| # | 情形 | 處理 |
|---|---|---|
| 1 | 發現測試報告造假 | 撤銷，90 天內不受理 |
| 2 | 插件後續版本引入嚴重問題 | 撤銷，需重新申請 |
| 3 | 作者主動申請撤銷 | 撤銷 |
| 4 | 發現認證範圍外的重大缺陷 | 評估後決定是否撤銷 |
| 5 | 證書信息被虛假使用 | 撤銷並公示 |

### 8.2 暫停的情形

| # | 情形 | 期限 |
|---|---|---|
| 1 | 收到有效投訴，正在調查 | 調查期間 |
| 2 | 插件從 registry 下架 | 立即暫停 |
| 3 | DSH 基準版本升級，尚未複測 | 至複測完成 |

**暫停期間證書仍可查詢，但標記為「暫停」。**

### 8.3 撤銷的程序

```
1. 书面通知申请人（说明理由与依据）
      ↓
2. 给 15 天申辩期
      ↓
3. 申辩成立 → 恢复；不成立 → 撤销
      ↓
4. 公开登记册更新
      ↓
5. 申请人可依 DSHIO/T 34 申诉
```

**不得未經通知直接撤銷。**

### 8.4 撤銷後的行為

- 公開登記冊標記「已撤銷」
- 證書查詢頁顯示撤銷日期與理由類別
- 作者必須在 7 天內移除標誌使用
- 逾期未移除的，公示違規

## 9 公開登記冊

### 9.1 內容

**所有證書（含已撤銷的）都必須公開可查。**

| 字段 | 說明 |
|---|---|
| 證書編號 | |
| 插件名與版本 | |
| 級別 | |
| 狀態 | 有效 / 暫停 / 已撤銷 |
| 發證日期 | |
| 有效期至 | |
| 報告連結 | |

### 9.2 查詢方式

**必須提供無需註冊的查詢：**

```
https://dshio.org/verify/<證書編號>
```

**也必須支持按插件名查詢：**

```
https://dshio.org/verify?plugin=dsh-pet
```

### 9.3 為什麼公開

1. **使用者的知情權** —— 看到標誌的人應該能核實
2. **防止偽造** —— 無法核實的證書等於沒有
3. **自我約束** —— 公開記錄使認證機構無法隨意發證

### 9.4 撤銷記錄保留

**已撤銷的證書不得從登記冊刪除。** 保留理由：已發布的引用需要能查到當時的狀態。

## 10 費用

### 10.1 當前狀態

**未定價。** 認證未啟用，因此沒有價格。

### 10.2 規劃中的考慮

| 因素 | 說明 |

| L1 靜態認證 | 成本極低（無容器、無人工），可能免費 |

### 10.3 免費額度

**規劃中：每個賬號每年 1 次免費的 L1 認證。** 用於讓作者先驗證流程。

## 檢測機構的多家制

### ⚠️ 當前狀態：不提供認證

**DSHIO 目前不頒發任何認證。** 認證僅在規劃中，尚未啟用。

本章描述的是**認證規則本身**（要滿足什麼、怎麼判），
**不預設認證由誰執行** —— 認證主體於啟用時另行公布。

### 認證與檢測分離

| 職能 | 現狀 | 若啟用的話 |
|---|---|---|
| **發布標準** | ✅ DSHIO 在做 | 不變 |
| **檢測** | ✅ **已開放**，符合 DSHIO/T 36 條件即可 | 不變 |
| **認證** | ❌ **不做** | **主體待定**，於啟用時另行公布 |

### 認證的技術依據

**若認證啟用**，將以檢測機構出具的報告為技術依據。

**接受條件：**

1. 報告來自 DSHIO/T 36 附表 A 中的認可機構
2. 報告在該機構的認可範圍內
3. 報告含 DSHIO/T 21 第 7 章要求的全部強制欄位
4. 報告的環境指紋與 DSHIO/T 21 一致
5. 對外發布的判定已執行 2 次且一致

**任一條不滿足，DSHIO 不得據以頒證。**

### 多家報告衝突時

同一插件、同一版本，兩家認可機構結論不同時，依 DSHIO/T 36 §7.2 處理：

1. 兩份報告都公開
2. 不得擇優採用
3. DSHIO 指定第三方機構複測
4. 以複測結論為準

### 為什麽認證不交給檢測機構

如果檢測機構也能頒證，它就同時是被監督者和監督者。

**檢測機構出報告，DSHIO 出認證** —— 兩個動作分開，
任何一方出問題都能被另一方與公眾發現。
