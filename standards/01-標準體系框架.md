# DSHIO 標準體系框架（v1.0 試行）

> 發布機構：DSHIO（DeepSeek Harness Input/Output）
> 域名：dshio.org（註冊中）
> 文件性質：體系框架文件，不作為標準被引用
> 日期：2026-11-07

---

## 一、為什麼需要一個體系，而不是一堆文件

**七份各自獨立的文件不叫標準體系，叫七篇文章。**

標準體系要解決三件事：

| 問題 | 體系怎麼解決 |
|---|---|
| 新標準該寫什麼、怎麼寫 | 編寫規則（DSHIO/T 01）|
| 標準之間怎麼引用才不循環 | 引用層級規則（本文件 §4）|
| 改一份，其他要不要跟著改 | 版本聯動規則（本文件 §7）|

## 二、四層結構

```
┌─────────────────────────────────────────┐
│  DSHIO/T 30–39   管理标准                │
│  认证、标志、申诉、修订                    │
│  回答：凭什么说它合规、不合规怎么办         │
└─────────────────────────────────────────┘
              ↑ 依据
┌─────────────────────────────────────────┐
│  DSHIO/T 20–29   方法标准                │
│  测试方法、测试条件、抽样、分级             │
│  回答：怎么测、在什么条件下测              │
└─────────────────────────────────────────┘
              ↑ 依据
┌─────────────────────────────────────────┐
│  DSHIO/T 10–19   产品标准                │
│  插件、套件、工具、接口、主题、模型接入      │
│  回答：对某类东西提什么要求                │
└─────────────────────────────────────────┘
              ↑ 全部引用
┌─────────────────────────────────────────┐
│  DSHIO/T 00–09   基础标准                │
│  术语、编写规则、分类编码、评定通则          │
│  回答：词是什么意思、文件怎么写            │
└─────────────────────────────────────────┘
```

**引用方向是单向的：上层可以引用下层，下层不得引用上层。**

理由：方法标准不应该依赖某个产品标准存在，否则加新产品标准就要改方法标准。

## 三、编号規則

### 格式

```
DSHIO/T 21—2026
│      │  │  └── 发布年份（首次发布年）
│      │  └───── 标准序号（两位，區段内递增）
│      └──────── T = 推荐性技术标准
└─────────────── 发布机构代号
```

**一切照 GB/T 體例，长破折号。**

### 序號區段

| 區段 | 類型 | 當前已分配 |
|---|---|---|
| **00–09** | 基礎標準 | 00 術語、01 編寫規則、02 分類與編碼、03 符合性評定通則 |
| **10–19** | 產品標準 | 10 插件、11 套件、12 工具、13 數據接口、14 主題界面、15 模型接入 |
| **20–29** | 方法標準 | 20 測試方法總則、21 測試條件、22 抽樣與複測、23 質量分級、24 風險分級 |
| **30–39** | 管理標準 | 30 收錄、31 推薦排名、32 認證規則、33 標誌使用、34 申訴複評、35 修訂程序 |

**預留空間：** 每區段還在用的號往後排，不跳號；廢止的號不重用。

### 為什麼不用 `DSHIO-DEV` 這種縮寫

**舊方案：**
```
DSHIO-DEV   开发规范
DSHIO-TEST  测试标准
```

**問題：**
1. 縮寫沒有順序，加標準要發明新縮寫
2. 沒法從編號看出類型
3. 引用時寫「DSHIO-TEST 3.2」不知道是產品標準還是方法標準

**新方案 `DSHIO/T 10—2026`：**
- `10` 一眼看出是產品標準區段
- 加標準就是加號
- 和 GB/T 一致，作者一看就懂

**舊縮寫保留為「代號」欄位：**

| 標準號 | 代號 |
|---|---|
| DSHIO/T 10—2026 | DSHIO-PLUGIN |
| DSHIO/T 20—2026 | DSHIO-TEST |
| DSHIO/T 23—2026 | DSHIO-GRADE |

**代號只用于非正式场合（如 URL 簡寫），正式引用必須用標準號。**

## 四、引用規則

### 三種引用形式

| 形式 | 寫法 | 適用 |
|---|---|---|
| **日期引用** | `DSHIO/T 00—2026` | 引用固定條款，被引標準改版不影響本標準 |
| **不注日期引用** | `DSHIO/T 00` | 引用最新版，被引標準改版自動跟隨 |
| **條款引用** | `DSHIO/T 00—2026 第 3.2 條` | 引用具體條款 |

**默認用「日期引用」** —— 標準的可預測性比自動更新更重要。

### 禁止循環引用

```
✗ DSHIO/T 10 插件标准 → 引用 DSHIO/T 12 工具标准 → 引用 DSHIO/T 10
```

**檢查方法：** 每份標準的「規範性引用文件」章節列出它引用的所有標準，形成有向圖，必須無環。

## 五、每份標準的強制結構

**照 GB/T 1.1 體例，八個章節，缺一不可：**

```
1  範圍
   —— 本標準規定了什麼、適用於什麼
   —— 一句話說清，不超過 3 行

2  規範性引用文件
   —— 只列「不引用就讀不懂」的文件
   —— 用日期引用

3  術語和定義
   —— 本標準特有的術語
   —— 通用術語引用 DSHIO/T 00，不重複定義

4  分類 / 要求對象
   —— 對什麼提要求（插件？套件？）
   —— 分類維度

5  技術要求
   —— 每一條都必須可測
   —— 禁止寫「應該友好」「性能良好」這類不可測的表述

6  試驗方法
   —— 引用方法標準，不自己寫測法
   —— 每條技術要求對應一個測法編號

7  檢驗規則
   —— 全檢還是抽檢
   —— 批次怎麼定義
   —— 判定規則（關鍵項 vs 一般項）

8  標誌、標籤
   —— 通過認證後怎麼標
   —— 引用 DSHIO/T 33 標誌使用
```

**如果一份文件寫不出第 5、6、7 章，它就還不是標準 —— 是說明書。**

## 六、版本與狀態

### 版本號

```
v<主版本>.<次版本>
```

| 位置 | 遞增條件 | 後果 |
|---|---|---|
| **主版本** | 不兼容的條款變更 | 原有認證失效，需重測 |
| **次版本** | 新增/澄清條款，向後兼容 | 原認證繼續有效 |

**標準號的年份不變** —— 年份是首次發布年，不是版本年。

### 狀態

| 狀態 | 含義 | 能不能用於判定 |
|---|---|---|
| **試行** | 已發布，試行期內可正常引用 | ✅（報告須注明「試行」）|
| **現行** | 當前有效 | ✅ |
| **即將實施** | 已發布未到實施日 | ⚠️ 參考，判定仍按現行 |
| **廢止** | 已被新版替代 | ❌ 僅存檔 |
| **草案** | 未發布 | ❌ 不得引用 |

**試行期規則：**

| 項 | 規定 |
|---|---|
| 試行期 | **2026-11-07 至 2027-02-07**（3 個月）|
| 期滿 | **自動轉為「現行」**，不需重新發布 |
| 期內 | 可正常引用、可用於檢驗判定，但報告須注明「依 DSHIO/T xx—2026（試行）」|
| 期內修訂 | 發現問題直接改，版本號保持 v1.0（試行期內不算不兼容變更）|
| 期滿後 | 任何條款變更按正常版本流程 |

### 版本聯動

**被引標準升主版本時：**

1. 所有引用它的標準必須評估
2. 評估結論寫入「標準修訂記錄」
3. 若本標準條款需改 → 本標準也升版本
4. 若不需要改 → 記錄「已評估，無需修改」

**這一步不能省。** 少了它，標準體系半年就散了。

## 七、標準修訂程序

### 誰能提

任何人都能提修訂建議（作者、使用者、我們自己）。

### 流程

```
1. 提議（寫清：改哪條、為什麼、影響誰）
        ↓
2. 公示（至少 14 天，公開收意見）
        ↓
3. 處理意見（每條意見都要回覆「採納」或「不採納 + 理由」）
        ↓
4. 發布（升版本號，寫變更記錄）
        ↓
5. 過渡期（至少 30 天，舊認證仍有效）
```

### 利益衝突聲明

**每一份標準的修訂記錄裡必須寫：**

> 本次修訂由誰提出、誰參與、是否有商業利益關聯。

**為什麼：** 我們自己也在做插件。如果不聲明，標準就成了給自己開後門的工具。

## 十、標準的起源與獨立性

### 11.1 起源：從官方開發套件引申

**DSHIO 標準不是憑空寫的。**

每一條技術要求都能追溯到官方開發套件中的一個具體事實：

| 標準條款 | 官方依據 | 取證方式 |
|---|---|---|
| 插件 manifest 必須有 `dsh.bundle.patch` | 第三方插件安裝機制 | `dsh plugin add` 實測 |
| `engines.dsh` 判版本兼容 | 官方 README 第 39 行 | 官方文檔 |
| 配置層優先序 | 官方 README 第 42–44 行 | 官方文檔 |
| entry / patch 欄位 | `dsh --dump-config-schema` | 導出 schema |
| 出廠 bundle 名 | 官方 README 第 46 行 | 官方文檔 |
| 模型接入由插件提供 | `dsh-llm-deepseek`、`dsh-llm-pi-ai` 是獨立插件 | 安裝目錄實查 |
| 官方插件共 150+ | `dsh --dump-default-config` | 實測輸出 |

**完整事實清單見同目錄 `00-官方DSH開發套件事實清單.md`。**

**原則：官方沒有的欄位，標準不得要求。**

DSHIO 不發明語法、不發明協議、不發明命令。它只做三件事：

1. **歸納** —— 把官方散落的約定整理成可查的條款
2. **篩選** —— 從「官方允許」中挑出「符合標準必須做到」的部分
3. **量化** —— 給出可測的閾值和可複現的條件

### 11.2 獨立性：不用官方套件也能按標準開發

**這是本標準體系的核心承諾：**

> **任何人不需要使用官方開發套件，也能依照 DSHIO 標準開發出符合標準的插件。**

**為什麼可以做到：**

| 標準只規定 | 標準不規定 |
|---|---|
| 產出物必須滿足的可觀測性質 | 用什麼語言寫（JS / TS / 其他均可）|
| 文件必須存在的欄位 | 用什麼編輯器、什麼構建工具 |
| 安裝後必須出現的狀態 | 內部代碼怎麼組織 |
| 配置樹中必須存在的 entry | 用什麼方式生成 patch 文件 |
| 工具的調用契約 | 是否使用 `defineTool()` 輔助函數 |

**具體含義：**

1. **不強制使用 `@deepseek-ai/dsh-tools`**
   `defineTool()` 只是寫工具的一種便捷方式。手寫一個符合 entry 契約的對象同樣合法。
   標準要求的是「工具可被調用」，不是「必須用某個庫」。

2. **不強制使用 TypeScript**
   官方插件用 TS 是因為官方項目用 TS。標準只要求運行時行為正確。

3. **不強制使用官方構建流程**
   標準不規定構建步驟，只規定產出物的結構。

4. **不強制使用特定包管理器**
   `dsh plugin` 當前轉發給 pnpm，但標準只要求「依賴能被正確解析」，不要求用 pnpm 開發。

5. **不強制使用 Cordis 的某個版本**
   只要插件在目標 DSH 版本上能掛載並運行，用哪個 Cordis 版本由作者決定。

### 11.3 如何保證「不用官方套件也合格」

**靠黑盒驗證，不靠白盒檢查。**

| 驗證方式 | 用不用 |
|---|---|
| **黑盒**：裝上、掛上、啟動、調用 | ✅ 標準的全部判定基於此 |
| 白盒：讀源碼、查是否 import 某個庫 | ❌ 不作為判定依據 |

**意涵：**

- 用 React 寫的插件和用純 JS 寫的插件，只要行為一致就同等合格
- 手工寫的 `cordis.patch.yml` 和生成的 patch，只要結構合法就同等合格
- 不讀作者的源代碼也能作出判定

> **這也保護了作者。** 標準不要求公開源碼，只要求公開行為。

### 11.4 對「官方套件」的準確定義

**「官方開發套件」指下列全部或部分：**

| 組件 | 包名 | 標準是否依賴 |
|---|---|---|
| CLI 啟動器 | `@deepseek-ai/dsh` | ✅ **依賴** —— 這是宿主，必須存在 |
| 工具定義輔助 | `@deepseek-ai/dsh-tools` | ❌ 不依賴 |
| 插件框架 | `@deepseek-ai/cordis` | ⚠️ 間接依賴（DSH 內部用它，但作者不直接調用也可以）|
| 官方插件集 | 150+ 個 `@deepseek-ai/dsh-*` | ❌ 不依賴 |
| 出廠 profile | web / headless / sdk 等 | ✅ 測試用 `web`，但標準不要求產品必須用某個 profile |

**結論：** 開發者只需要 **一個能運行的 DSH**。其餘一切可自選。

### 11.5 這條原則怎麼寫進每份標準

**每份標準的第 1 章「範圍」之後，必須有一段：「實施獨立性聲明」**

範本：

> **實施獨立性。** 本標準不要求使用任何特定的開發工具、編程語言、構建流程或輔助庫。
> 凡滿足本標準全部技術要求者，即為符合，不論其如何實現。
> 判定以可觀測的運行時行為為準，不以源碼結構為準。

**缺少這段聲明的標準，不得從「試行」期滿轉為「現行」。**

## 十一、與官方開發套件的關係


**原則：DSHIO 標準不發明技術，只歸納官方事實並提出可驗證的要求。**

|---|---|

1. 先更新事實清單
2. 再評估哪些標準受影響
3. 走修訂程序
